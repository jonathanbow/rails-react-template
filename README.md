# Rails + React Template

A full-stack starter for building apps with a **Rails** backend and a **React 19 + TypeScript** frontend, glued together with [Inertia.js](https://inertia-rails.dev). You write Rails controllers and React pages, with no separate API and no client-side router.

It ships with working authentication, a settings area, a dashboard, a shadcn/ui component library and a production `Dockerfile`, so you can start on your own features straight away.

## What's included

| Area | Details |
| --- | --- |
| Backend | Rails, PostgreSQL, RSpec + FactoryBot |
| Frontend | React 19, TypeScript, Tailwind CSS 4, [shadcn/ui](https://ui.shadcn.com) (Radix) |
| Glue | `inertia_rails` and Vite (`rails_vite`), with typed route helpers generated by Typelizer |
| Auth | Hand-rolled, [Authentication Zero](https://github.com/lazaronixon/authentication-zero) style: sign up/in, email verification, password reset, session management. No Devise. |
| Pages | Home, dashboard, and settings (profile, email, password, active sessions, appearance with light/dark mode) |
| Deploy | Production `Dockerfile` (works with Railway, Render or any Docker host), with optional SSR |

## Prerequisites

- **Ruby** 4.0.1 (see `.ruby-version`)
- **Node.js** 22.23.2 (see `.node-version`)
- **PostgreSQL** running locally

Use a version manager such as `mise`, `asdf` or `rbenv`/`nvm` to match the pinned versions.

## Getting started

```sh
git clone <your-repo-url> myapp
cd myapp
bin/setup
```

`bin/setup` installs gems and npm packages, creates and migrates the database, then starts the dev server. Open <http://localhost:3000> and click **Sign up** to create an account.

Setup options:

- `bin/setup --skip-server` sets everything up without starting the server
- `bin/setup --reset` also resets the database

Day to day, start the app with `bin/dev`. It runs Rails on port 3000 and the Vite dev server together (see `Procfile.dev`), with hot reloading for the frontend.

### Database

The app connects to PostgreSQL using `config/database.yml`. By default it uses your local socket and your OS user. If you need something different, set `DATABASE_URL`, or `DB_HOST`, `DB_USER` and `DB_PASSWORD`.

Databases are named `rails_react_template_development` and `rails_react_template_test`. Rename them in `config/database.yml` when you make the app your own.

### Emails in development

Verification and password-reset emails open in your browser through [letter_opener](https://github.com/ryanb/letter_opener), so you don't need any mail setup to try the auth flows.

## Making it your own

Do this first, before you build on the template:

1. **Rename the app.** Search for `rails_react_template`, `rails-react-template` and `RailsReactTemplate` and replace them. The main places are:
   - `package.json` and `package-lock.json` (`name`)
   - `config/database.yml` (database names)
   - `config/application.rb` (module name)
   - `config/deploy.yml` (Kamal service and image names)
   - `app/views/pwa/manifest.json.erb` (PWA name)
   - `Dockerfile` (comment examples)
2. **Create credentials.** The template doesn't ship a `config/credentials.yml.enc`, and `bin/setup` doesn't create one. Development and test work without it, but production needs it. Run `bin/rails credentials:edit` to generate your own encrypted credentials file and `config/master.key` (save and close the editor to write them). Commit `config/credentials.yml.enc`, but never commit `config/master.key`, which is gitignored. Keep the key in a password manager, because deploys read it (`RAILS_MASTER_KEY` in `.kamal/secrets` and in the Railway variables below).
3. **Swap the branding.** The logo lives in `app/javascript/components/app-logo.tsx`.
4. **Update this README and `CLAUDE.md`** to describe your app.

## How the code is organised

```
app/
  controllers/       Rails controllers (inherit from InertiaController)
  models/            User, Session, Current
  javascript/
    entrypoints/     inertia.tsx boots the React app
    pages/           One React component per controller action
    layouts/         persistent-layout plus app, auth and settings layouts
    components/      App components; components/ui holds shadcn/ui primitives
    hooks/ lib/      Shared hooks and utilities
    routes/ types/   GENERATED. Do not edit by hand
config/routes.rb     Routes
spec/                RSpec specs (models, requests, mailers) and factories
```

### How a page gets rendered

Controllers inherit from `InertiaController`, which renders a React page automatically. An action with no explicit `render` renders the component at `app/javascript/pages/<controller_path>/<action>.tsx`. For example, `DashboardController#index` renders `pages/dashboard/index.tsx`.

Pass data to the page by assigning props in the controller (see `inertia_rails` docs). The signed-in user is available everywhere as a shared prop (`auth.user`).

For a static page that needs no controller, declare it in the routes file, like `inertia :appearance` in `config/routes.rb`.

### Adding a page: quick walkthrough

1. Add a route in `config/routes.rb`:
   ```ruby
   resources :projects, only: [:index]
   ```
2. Create `app/controllers/projects_controller.rb`:
   ```ruby
   class ProjectsController < InertiaController
     def index
       render inertia: { projects: Project.all.as_json(only: %i[id name]) }
     end
   end
   ```
3. Create `app/javascript/pages/projects/index.tsx` and export a React component that receives `projects` as props.
4. Regenerate the typed route helpers (next section).

Every controller requires a signed-in user by default. Public controllers must skip `authenticate`.

### Generated TypeScript

Typed route helpers (`app/javascript/routes/`) and types (`app/javascript/types/`) are generated by [Typelizer](https://github.com/skryukov/typelizer). After changing routes, controllers or serializers, run:

```sh
bin/rails typelizer:generate:refresh
```

Then import helpers from the generated module:

```ts
import { dashboard } from "@/routes"
```

Commit the generated files. CI fails if they are stale. Use the `@/` alias for anything under `app/javascript/`.

### Adding UI components

The project is set up for the shadcn CLI (`components.json`):

```sh
npx shadcn@latest add dialog
```

Components land in `app/javascript/components/ui`.

## Common commands

| Command | What it does |
| --- | --- |
| `bin/dev` | Run Rails and Vite together |
| `bin/rspec` | Run all specs. For one example, use `bin/rspec spec/models/user_spec.rb:12` |
| `bin/rubocop` (`-a` to autocorrect) | Ruby lint |
| `npm run lint` / `lint:fix` | ESLint |
| `npm run format` / `format:fix` | Prettier |
| `npm run check` | TypeScript type check |
| `bin/ci` | The full CI pipeline (see below) |

`bin/ci` runs RuboCop, JS lint/format/type checks, the generated-types freshness check, bundler-audit, npm audit, Brakeman, RSpec and a seed check. Run it before opening a PR. GitHub Actions runs the same checks (`.github/workflows/ci.yml`).

## Testing

Specs live in `spec/{models,requests,mailers}` and use RSpec, FactoryBot, shoulda-matchers and SimpleCov. There are no system tests. `spec/factories_spec.rb` checks that every factory is valid, so add a factory for each new model.

```sh
bin/rspec
```

## Authentication

- Sign up and sign in at `/sign_up` and `/sign_in`.
- Sessions are stored in the `Session` model and tracked with a signed `session_token` cookie. `Current` holds the per-request session and user, along with the user agent and IP address shown on **Settings → Sessions**.
- `ApplicationController` runs `authenticate` on every request. Public controllers skip it and use `require_no_authentication` so signed-in users are redirected away.
- Email verification and password reset live under `Identity::`, and account management under `Settings::`.

## Deploying

The repo includes a production `Dockerfile`, so any platform that builds Docker images will work. The steps below use [Railway](https://railway.com) as the example. Render is similar. These are suggestions to get you started, not a tested recipe.

1. **Create a project** on Railway from your GitHub repo. Railway detects the `Dockerfile` and builds from it.
2. **Add a PostgreSQL database** to the project and expose its URL to your app as `DATABASE_URL` (for example by referencing the database service's variable).
3. **Set environment variables** on the app service:
   - `RAILS_MASTER_KEY`: the contents of your `config/master.key`
   - `DATABASE_URL`: from step 2
   - `SOLID_QUEUE_IN_PUMA=true`: runs background jobs inside the web process
4. **Deploy and generate a domain** for the service in Railway's networking settings.
5. **Set the health check path** to `/up`, if the platform asks for one.

Things to check on a first deploy:

- **Database layout.** `config/database.yml` expects separate PostgreSQL databases in production for the primary data, cache, queue and cable (Solid Cache, Solid Queue and Solid Cable), each with a hardcoded name. Hosted platforms usually give you a single database. If the app fails to boot or migrate, the simplest fix is to point the cache, queue and cable entries at that same database. Check the Rails multi-database docs for the details.
- **Migrations.** The Docker entrypoint (`bin/docker-entrypoint`) runs `bin/rails db:prepare` each time the server starts, so you don't need a separate release command.
- **Port.** The container starts [Thruster](https://github.com/basecamp/thruster) in front of Puma, and it listens on port 80 by default. If the platform expects the app on its own `PORT` value, set `HTTP_PORT` to match.
- **HTTPS.** The platform terminates TLS. Once it works, uncomment `config.assume_ssl = true` and `config.force_ssl = true` in `config/environments/production.rb`.
- **Email.** Production has no mail provider configured. Add SMTP or an API-based provider before relying on email verification and password reset.

Prefer to run your own server? [Kamal](https://kamal-deploy.org) works with this `Dockerfile`. The repo still contains a starter `config/deploy.yml` and `.kamal/` directory from the generator. You can configure and use them, or delete them if you don't need them.

### Server-side rendering (SSR)

SSR is enabled by default. A Puma plugin (`plugin :inertia_ssr` in `config/puma.rb`) runs the Node renderer in-process, so you don't need a separate service. If SSR ever fails, Inertia falls back to client-side rendering (see `config.on_ssr_error`).

- **In development**, Vite serves SSR itself, so there is nothing extra to run.
- **In production**, the Docker image must include the SSR bundle. The `Dockerfile` builds it when the `SSR_ENABLED` build arg is `true`, which is the default. On Railway, build args come from service variables, so you can set `SSR_ENABLED` there if you want to be explicit.
- **To turn SSR off**, set `config.ssr_enabled = false` in `config/initializers/inertia_rails.rb` and build with `SSR_ENABLED=false`. The image is then smaller because it ships without Node.

## Troubleshooting

- **`PG::ConnectionBad` on setup.** PostgreSQL isn't running or the credentials are wrong. Check `pg_isready`, then set `DATABASE_URL` or `DB_HOST`/`DB_USER`/`DB_PASSWORD`.
- **Wrong Ruby or Node version.** Install the versions in `.ruby-version` and `.node-version`.
- **CI says generated types are stale.** Run `bin/rails typelizer:generate:refresh` and commit the result.
- **Blank page or missing assets in dev.** Make sure Vite is running. Use `bin/dev`, not `bin/rails s` on its own.
